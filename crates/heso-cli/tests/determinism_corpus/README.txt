# Determinism Conformance Corpus

This directory is the evidence behind **LEG 1 (record / replay)** of the
Heso trust model — the hero claim that anyone can re-run an operator's
recorded bytes through the engine and get a **byte-identical** plat (the
same `plat_hash`). It is the proof that LEG 1 catches a lying summarizer
and needs **no notary**.

## What's here

- `manifest.json` — one pinned record per cassette:
  `{cassette, input_plat, seed, engine_id, expected_plat_hash, hydrated}`.
  Checked in; regenerated by the blessing test, never hand-edited.
- `fixtures/*.plat` — checked-in input plats, each embedding its own
  cassette. `heso run` replays them with **zero network** — the canonical
  origin (`http://heso.invalid`) is never bound; the cassette is read from
  inside the plat.
- `fixtures/hydrated_spa.html` + `hydrated_spa_data.json` — the one
  JS-hydrated fixture. It drives `fetch()` + `Math.random()` +
  `crypto.randomUUID()` + `Date.now()` + UTC `Date` accessors and mutates
  the DOM in a resolved-fetch microtask, so it exercises the QuickJS
  determinism fences (seeded ChaCha20 RNG, virtual clock, pinned UTC tz)
  through `plat_hash`. This was the single biggest pre-existing coverage
  gap: no JS-hydrated cassette was routed through `plat_hash` anywhere.

## The harness (`tests/determinism_conformance.rs`) — the gate

For every cassette it:

1. Checks the running binary's `engine_id` against the manifest's.
   `engine.version` (`CARGO_PKG_VERSION`) lives in the hash region, so a
   version bump changes `plat_hash` **by design**. A mismatch is reported
   as `EXPECTED DRIFT: regenerate`, **not** a determinism failure. A hash
   mismatch with a **matching** `engine_id` is a real determinism bug.
2. Spawns **K = 16 fresh OS processes** running
   `heso run --seed 0 <fixed.plat>`, each with a perturbed environment so
   the process-global HashMap `RandomState` seed and allocator layout
   differ. Fresh processes are mandatory: an in-process loop reuses one
   `RandomState` seed and hides exactly the HashMap-order-into-signed-bytes
   hazards this is built to catch.
3. Asserts all 16 hashes are byte-identical to each other **and** to the
   pinned `expected_plat_hash`.
4. Cross-checks every plat against the dependency-free `heso-verify`
   binary (BLAKE3 over `serde_jcs` canonical bytes, zero engine deps). If
   `heso run`'s self-reported hash and `heso-verify`'s independent
   recompute ever disagree, that is a producer/verifier canonicalization
   split — it fails loud.

## Regenerating (BLESS)

The corpus is **computed**, never hand-authored — same discipline as the
reseed goldens and `generate_vectors.rs`. After an intentional
`engine.version` bump (or adding a cassette), re-mint it:

```sh
cargo test -p heso-cli --test determinism_generate -- --ignored --nocapture
```

The generator serves each cassette body on an **ephemeral** loopback port
(no fixed-port `TIME_WAIT` race), stamps a one-step `open`, rewrites the
volatile origin to the canonical host, recomputes the hash, and rewrites
`manifest.json`. Review the diff before committing.

## Cross-architecture honesty — read this before citing the proof

**K = 16 fresh processes on ONE machine proves determinism across HashMap
`RandomState` + allocator entropy + process boundaries on THAT (arch, OS,
toolchain) only.** It does **not** prove cross-architecture / cross-OS
byte-identity.

Cross-arch byte-identity depends on `rand_chacha` (ChaCha20, chosen over
the non-portable `StdRng` precisely for cross-host portability),
`serde_jcs` ECMA-262 number formatting, BLAKE3, and the vendored
QuickStop-NG (hesojs) fork all producing identical bytes on
aarch64-vs-x86_64 and macOS-vs-Linux.

We deliver: (1) this K-process harness, (2) the pinned hashes generated on
a named reference target (`manifest.json#reference_target`), and (3) a CI
matrix (`.github/workflows/determinism-matrix.yml`) that runs the same
harness and asserts the same pinned hashes on
`{x86_64-linux, aarch64-linux, x86_64-macos, aarch64-macos}`.

> **Single-host K-process determinism is proven here; cross-arch
> byte-identity is enforced by the CI matrix, and any matrix divergence is
> a release blocker, not a warning.** Until that matrix is green across all
> four targets, cross-arch determinism is an **asserted design goal** backed
> by ChaCha20/JCS/BLAKE3 portability — **not** a proof. Do not let any doc
> overclaim it from one developer machine.

## Known live hazards the harness EXPOSES (treat a flap as the bug)

- **Cookie array order** (`render_cookies`) was HashMap-iteration-order and
  reaches signed bytes via `read --include cookies` / `serve`. Fixed by
  sorting `(name, domain, path)`; regression-pinned in
  `tests/cookie_order_determinism.rs`.
- **Wall-clock DOM settling** made async-mutating pages capture differently
  per run. The plan `open` path now settles on the **virtual-clock fixed
  point** (`settle_dom_deterministic`), never `Instant::now()`. If the
  hydrated cassette ever flaps across the 16 processes, that flap **is** the
  bug — file it; do not paper over it with retries.

## Hazard-coverage fixtures (which fixture covers which fix)

Three fixtures extend the corpus to cover specific plat-byte hazards. Each
names the production fix it pins and whether reverting that fix REDDENS the
MAIN corpus (the `assert_eq` pin mismatch / distinct-hash assert):

- `multi_cookie` — the response `cookies[]` array. The corpus generator
  serves six `Set-Cookie` headers in reverse-sorted name order; `cmd_run`/
  `cmd_stamp` reconstruct them from the cassette's recorded
  `response_headers` (`response_cookies_from_headers`) and `render_cookies`
  sorts by `(name, domain, path)`. The cookies land in the SIGNED replay
  body (`body["cookies"]`). **Reverting the `render_cookies` sort REDDENS
  `multi_cookie`** (verified: the array follows header order, so the pinned
  hash stops reproducing). This is the run-corpus counterpart of the
  read-surface `cookie_order_determinism.rs` side test.

- `chained_settle_spa` — the settle loop's virtual-clock advance branch. A
  CHAIN of non-zero (50 ms) `setTimeout` stages that `run_pending_jobs`
  alone never fires; only `settle_dom_deterministic`'s
  `if pending_timers > 0 { advance_clock(SETTLE_VIRTUAL_TICK_MS) }` branch
  drives them across multiple virtual ticks. **No-op'ing that branch
  REDDENS `chained_settle_spa`** (verified) while the single-microtask
  `hydrated_spa` fixture stays green — which is exactly why the chained
  fixture is needed.

- `data_attr_heavy` — the `data_attrs::extract` -> `body["data_attrs"]`
  path through the signed hash (the only corpus fixture carrying a rich
  `data_attrs` blob). **HONEST CAVEAT:** the BTreeMap-vs-HashMap key ORDER
  is NOT a `plat_hash` hazard, because `serde_jcs::to_vec` sorts every JSON
  object's keys recursively before hashing — so the `BTreeMap -> HashMap`
  mutation does NOT redden this fixture (verified empirically). The
  structural protection for object-key order is JCS canonicalization, not
  the container type. This fixture is data_attrs PATH coverage (guarded by
  `saw_data_attrs` against silent removal), not a redden-on-mutation proof.
  Container-order hazards that DO reach the hash live behind ordered ARRAYS
  (see `multi_cookie`'s `cookies[]`), which JCS does NOT reorder.

The conformance harness asserts `saw_data_attrs` and `saw_settle_chain`
(alongside `saw_hydrated`) so a regenerate that silently dropped one of
these fixtures fails loud.

## Determinism depends on the vendored QuickJS fork

If a stock `rquickjs-sys` ever resolves instead of the vendored
`heso-quickjs-sys` `[patch.crates-io]`, `JS_SetClockSource` /
`JS_SetRandomSource` are absent and QuickJS silently falls back to
wall-clock + time-seeded xorshift — nondeterministic plat bytes with **no
error**. The `hydrated_spa` cassette is the only guard against that
regression; omitting it would let the bug ship silently.
